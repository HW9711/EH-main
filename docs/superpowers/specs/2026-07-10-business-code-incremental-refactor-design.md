# 主控业务代码渐进简化重构设计

## 1. 设计结论

本工程采用“行为锁定、一次一个模块、实机确认后提交”的渐进重构方式。

业务源码唯一基线为提交 `a39c3b1`：

- 提交时间：2026-07-09 18:29。
- 提交说明：修正泵压力保护与分体手柄状态保持。
- 该版本已经过大量实机测试，是后续业务重构的行为真值。

本设计明确放弃以下做法：

- 不从 `c35c404` 或旧实验工作区复制代码。
- 不同时修改任务调度、脚踏、泵、外控和构建架构。
- 不恢复单软任务调度器。
- 不删除独立任务栈、静态 TCB 或全局业务运行互斥锁。
- 不用文件数量、ROM/RW 降低或编译通过代替实机验证。
- 不使用 `UIDP_PUMP_DISPLAY_AB_MIRROR_SWAP_ENABLE=1U` 的屏幕局部镜像补丁。

## 2. 目标

### 2.1 主要目标

- 减少 A/B 通道复制代码，尤其是手柄扫描和泵行为。
- 缩短大型业务函数，使每个函数只完成一个可以直接说明的业务动作。
- 明确识别暂存、通道记忆、当前工作状态、泵状态、控制权和报警的所有者。
- 删除当前构建已证明无运行路径的旧业务代码，但保留工厂模式和安全启动需要的入口。
- 让注释直接说明运行时机、状态变化、硬件动作和保留原时序的原因。
- 每个阶段都能够独立构建、独立烧录、独立验证、独立回退。

### 2.2 非目标

- 不改变通信协议、CRC、帧字段、EEPROM 页面布局或 UI 地址。
- 不改变 GPIO、I2C、UART、压力输入和泵驱动映射。
- 不改变任务周期、队列长度、等待时间、阻塞延时和任务注册顺序。
- 不改变安全门禁、控制权规则、报警码、压力锁止或重新启动条件。
- 不在业务重构阶段顺手修复尚未经过专项验证的疑似缺陷。
- 第一轮不移动 `User/Application/Beep` 下历史文件的位置。
- 不建立 Repository、Service、Facade、EventBus 等通用框架。

## 3. 当前工程主要问题

| 文件 | 物理行数 | 当前混合职责 |
| --- | ---: | --- |
| `User/Application/Pubinterface/Pubinterface.c` | 4712 | 当前工作状态、通道记忆、泵、显示、报警、控制权、各输入动作 |
| `User/Application/Handle/handlescan.c` | 3431 | A/B 短接、去抖、EEPROM、RFID、报警、上线事件 |
| `User/Application/ExternalComm/external_comm_task.c` | 3017 | 收包 FIFO、协议命令、EEPROM、控制、超时、报警、心跳 |
| `User/Application/Beep/sscFOOT.c` | 1525 | 脚踏收包、定标值、三类脚踏状态机、控制权、泵联动 |
| `User/Peripheral/uart/soft_uart.c` | 1419 | 位级软串口、CS1237 协议、设备识别、泵遥测更新 |
| `User/Application/Beep/sscUIDP.c` | 1078 | UI 队列、开机绘制、补刷、A/B 泵和手柄显示 |
| `User/Application/Beep/sscRFID.c` | 951 | 硬件通道、请求队列、协议、缓存和兼容入口 |

`Pubinterface.h`目前还存在以下问题：

- 被 18 个业务或外设源文件直接包含。
- 暴露约 60 个函数声明和 179 个宏。
- 同时定义业务枚举、报警码、UI 区域、数据结构、可写全局变量和动作接口。
- 没有 include guard。

当前最严重的问题不是目录层级，而是公共状态拥有多个直接写入者：

- `WorkMessage`由 Pubinterface、脚踏、外控、手柄扫描、实体键、电机回包和按键行为写入。
- `MemoryMsgA/B`由 Pubinterface、外控、脚踏、实体键和手柄扫描写入。
- `pumpMessageA/B`同时承载设备识别、压力遥测、控制请求、闭环输出、压力锁止和排空计时。
- `s_control_owner`是少数边界清楚的状态，只由 `ControlArbitration_*()`写入。

## 4. 必须冻结的产品行为

### 4.1 任务模型

- 保留每个软任务独立的静态 FreeRTOS 线程栈。
- 保留每个任务自己的静态 TCB。
- 保留 `AppTaskRuntimeGate()`全局运行互斥锁。
- 业务回调继续依赖该互斥锁串行访问全局状态。

### 4.2 17 个实际运行入口

| 入口 | 周期 |
| --- | ---: |
| Motor UART 回包 | 3ms |
| 手柄扫描 | 10ms |
| 脚踏解析 | 10ms |
| UI 显示 | 10ms |
| 外控通信 | 10ms |
| A 泵行为 | 25ms |
| B 泵行为 | 25ms |
| 脚踏行为 | 25ms |
| 屏幕按键 | 30ms |
| 按键行为 | 30ms |
| 手柄实体键 | 30ms |
| 电机控制 | 50ms |
| 蜂鸣 | 100ms |
| RFID | 100ms |
| 压力软串口 | 100ms |
| LED | 200ms |
| 看门狗任务 | 300ms |

`PedalRecvTask_Init()`虽然存在，但当前没有接入 `Userparser_Init()`，不得把它误算成运行任务或在重构中擅自启动。

### 4.3 启动顺序

以下顺序必须保持：

1. 板级 GPIO。
2. EEPROM 和主控软件版本同步。
3. UART1、UART2、UART3、可选 UART9、UART4、UART5、UART6、UART7。
4. 启动页和上电停止帧。
5. 公共状态初始化。
6. RFID 初始化。
7. 按 `Userparser_Init()`当前顺序创建业务任务。

### 4.4 A/B 映射

```text
PE4 / SIM_UART_1 -> pumpMessageA -> A 泵显示 -> 左侧 A
PE6 / SIM_UART_2 -> pumpMessageB -> B 泵显示 -> 右侧 B
逻辑 A 泵驱动 -> UART5
逻辑 B 泵驱动 -> UART7
屏幕 A 泵按键 -> 只操作逻辑 A
屏幕 B 泵按键 -> 只操作逻辑 B
UIDP_PUMP_DISPLAY_AB_MIRROR_SWAP_ENABLE -> 0U
```

任何阶段都必须同时检查输入、业务状态、输出、显示和触摸五层，禁止只在其中一层交换 A/B。

### 4.5 手柄异步状态链

必须保留以下异步过渡：

```text
handlescan 写 ChannelrecognizeMessageA/B
    -> 投递 PLUG/UNPLUG 事件
    -> sscKEYBH 以 30ms 周期消费事件
    -> PlugORunPLUGActive 写 MemoryMsgA/B
    -> 满足选择条件时装载 WorkMessage
```

插拔事件尚未消费时，外控心跳仍会从识别暂存读取兜底信息。不得把该链改成 handlescan 同步写完整 `WorkMessage`。

## 5. 目标责任边界

### 5.1 手柄识别

- `handlescan`负责短接、去抖、EEPROM/RFID 读取和 `ChannelrecognizeMessageA/B`内容。
- 插拔业务事件仍通过现有按键行为队列发送。
- 通道记忆和当前通道选择继续由 Pubinterface 处理。

### 5.2 通道记忆和当前工作状态

- `ChannelrecognizeMessageA/B`表示本次识别暂存。
- `MemoryMsgA/B`表示 A/B 通道长期记忆。
- `WorkMessage`表示当前选中通道的运行快照。
- 不给每个字段增加 getter/setter，只建立少量完整业务动作，例如装载通道、设置速度、请求启动、请求停止和故障安全停止。

### 5.3 控制权

- `s_control_owner`只由 `ControlArbitration_*()`维护。
- 本地控制只有在运行请求清除且驱动反馈归零后才释放。
- 外控 owner 不因电机暂时停止自动释放。
- 外控重复保活不能重复执行停输出。
- 非外控运行期间收到外控退出命令，不得停止本地运行。

### 5.4 泵状态

- `soft_uart.c`只负责设备识别和压力遥测。
- 屏幕、脚踏、手柄联动和外控通过明确的泵请求动作设置启停、速度和排空。
- A/B 泵任务只负责压力闭环、压力锁止、实际输出和 UART 帧。
- `speed_work`继续表示设定值，`speed_output`继续表示闭环后的实际输出，两者不得合并。
- 压力锁止只能由新的启动沿清除，压力自然下降不得自动恢复。

### 5.5 报警

继续区分三类状态：

- `WorkMessage.alarm_*`：持续、会阻塞控制的真实报警。
- `SendAlarmMessageTimed()`：限时蜂鸣。
- 临时 UI 或外控提示：不写全局报警。

手柄 A/B 校验报警清除时，必须继续检查另一通道是否仍有报警，不能直接调用无条件清除。

### 5.6 外控

外控最终按四段数据流组织：

- 接收 FIFO 和完整帧提取。
- 命令校验和业务执行。
- 报警及心跳状态组装。
- 10ms 任务入口和链路超时。

`external_comm_protocol.c`继续只负责协议解析和组帧，不进一步拆分。

## 6. 分阶段实施设计

### 阶段 0：基线行为锁定

- 保存 `a39c3b1` 的 HEX、map、构建日志和源文件清单。
- 固定 17 个任务周期、启动顺序和 A/B 映射。
- 为当前阶段建立输入、状态、输出对照表。
- 临时校验脚本执行后立即删除；需要长期保留的测试资产先取得用户同意。

### 阶段 1：`handlekey.c`低风险试点

- 删除 map 已确认不进入镜像的旧扫描入口和仅被旧入口调用的函数。
- 保留当前真实入口 `HANDLEKEYTaskFunc()`到 `HandleKey_ScanRunKeys()`。
- 保持实体键启动、停止、控制权、模式提示和联动泵顺序。
- 为所有触碰函数补齐三项中文函数注释。

该阶段用于验证“小范围修改、构建、烧录、用户确认、提交”的完整流程是否可靠。

### 阶段 2：`handlescan.c`分三步简化

每一步都形成独立烧录版本：

1. 集中 A/B 通道上下文，但暂不合并两份主状态机。
2. 让 EEPROM、重试、报警、RFID 等公共辅助函数统一接收通道上下文。
3. 合并 A/B 主状态机为一个私有执行函数。

必须保留：

- `HandlescanA_Fun_SSC()`和 `HandlescanB_Fun_SSC()`两个调试入口。
- `Handlescan_Fun()`严格先 A 后 B。
- A 使用 I2C2，B 使用 I2C3。
- 插入、拔出、认证、重试、报警和 RFID 时序。
- 运行中插入另一通道不抢占当前通道。
- 运行中拔出当前手柄立即进入现有安全停止链。

### 阶段 3：A/B 泵行为共用内核

- 保留两个任务、两个队列、两个静态线程栈和两个公共初始化入口。
- 把类型换算、排空、压力保护、输出发布等相同逻辑收进一个直接承担泵行为的公共实现。
- 继续保持 A/B 映射、25ms 周期、6 字节帧和重复发送时序。
- 暂不删除 `pump.c` 中仍被故障路径调用的 A 泵直接输出入口。

### 阶段 4：`sscFOOT.c`同文件拆函数

- 将长函数拆为 JT、JTB、JTD 三个处理函数。
- 再抽取公共门禁、启动、释放、跨通道切换和注水泵联动。
- 第一轮不移动文件，不改变任何分支顺序。
- A/B 差异先记录为行为，不在机械拆函数时修正。

### 阶段 5：电机、按键、屏幕和 UI

以下每项都是独立烧录版本，不合并实施：

- `sscDrive.c`：按速度源、倍率、补偿、方向、通道、显示、发送整理 `MOTORRUN()`。
- `motoruartdata.c`：拆成候选帧校验、反馈发布、故障边沿处理。
- `sscKEYBH.c`：整理五类来源分发，保留来源语义和队列排空顺序。
- `screenkey.c`：分开帧提取、键值转换和保活处理。
- `sscUIDP.c`：分开单条消息处理、开机绘制和补刷；合并 A/B 泵显示重复实现。

### 阶段 6：收敛 Pubinterface 所有权

按以下顺序独立实施：

1. 控制权仲裁。
2. 通道识别和通道记忆。
3. 当前工作状态动作入口。
4. 泵请求入口。
5. 报警生命周期。
6. 最后缩小 `Pubinterface.h`。

只有职责已经稳定、调用者已经切换后，才允许新增少量直接承担职责的文件，例如：

- `control_arbitration.c/.h`
- `channel_memory.c/.h`
- `work_alarm.c/.h`

调用者直接包含新模块头文件，不在 `Pubinterface`中再建立纯转发包装。

### 阶段 7：外控、RFID 和软串口

- 外控按接收、命令、状态上传和任务入口逐段拆分。
- RFID 收敛请求、停止、结果复制和协议解析入口。
- 软串口保留位级驱动，将 CS1237 协议解析和泵遥测发布整理成明确业务段。
- 每次只处理一个模块，协议字节和时序保持不变。

### 阶段 8：构建清单和文档收尾

- 只有新增或删除源文件时才同步 EIDE 和 Keil 清单。
- 修正与当前源码不一致的压力映射、任务周期和状态说明。
- 清理确认无引用的宏、声明和兼容文件。
- 不为了目录整齐移动仍在工作的源码文件。

## 7. 独立缺陷队列

以下问题不与机械重构混合，每项都需要单独复现、修复、测试和提交：

- `ScreenKey_Scan()`的 `dat1[16]` 长度上限缺失和噪声前缀剩余长度问题。
- `handlescan.c`刀具配置查表返回空指针后仍可能解引用。
- RFID 请求尝试次数递减被注释，实际行为与注释不一致。
- 右脚踏某分支检查左踏控制标志，以及 A/B 注水泵启动速度来源不一致。
- 电机故障期间运行请求和 A/B 泵停止路径不对称。
- 连续电机回包扫描可能跳过紧邻第二帧起点。
- 插拔事件在全局运行互斥锁内等待 60ms，无法让消费者及时进入回调。
- 蜂鸣报警去重、队列满和普通按键清持续报警之间的生命周期冲突。
- 看门狗初始化和刷新被注释，300ms任务实际为空动作。

旧记录中的“刚好 12 字节电机回包必然漏解析”已经重新计算并确认不成立，不进入缺陷队列。

## 8. 验证和提交闸门

### 8.1 本机验证

每个阶段至少完成：

- `git diff --check`。
- 修改文件编码和中文注释检查。
- AC5/EIDE 全量构建 0 error，warning 不增加。
- Keil 工程构建或至少确认源文件清单一致。
- map 对比任务栈、目标符号、RO、RW 和 ROM。
- 当前模块输入、状态和输出对照。
- UART 或屏幕协议逐字节对照。

### 8.2 实机验证

本机构建通过后，由用户烧录并完成与当前模块对应的实机测试。至少覆盖：

- 上电和启动页。
- A/B 单独及组合上线。
- 当前通道切换、运行中插拔和空闲回落。
- 脚控、手控、触控和外控互斥。
- A/B 泵上线、启停、调速、排空和压力停泵。
- RFID 掉标签、重新识别和相同 EPC 参数保持。
- 外控心跳、断线停输出和释放控制权。

### 8.3 Git 提交

严格执行以下顺序：

1. 完成一个模块的修改。
2. 完成本机静态检查和全量构建。
3. 用户烧录实机测试。
4. 用户明确回复该阶段无问题。
5. 再按工程要求提交 Git。
6. 提交后才允许开始下一阶段。

如果实机出现任何行为差异，只回退当前阶段，不继续后续模块。

提交信息使用中文业务标题，正文使用 `•` 说明改动、运行影响、清理和验证范围。

## 9. 注释规则

所有新增、重写或大幅调整的业务函数必须包含：

- 函数功能。
- 输入参数。
- 返回参数。

函数内部注释重点说明：

- 本逻辑什么时候运行。
- 修改了哪个状态。
- 为什么必须保持当前顺序或时间。
- 最终影响哪个硬件、屏幕区域、协议字段或安全门禁。

禁止使用“处理数据”“执行逻辑”“记得修改”“暂时这样”等无法帮助现场维护的注释。

## 10. 完成标准

本轮业务重构全部完成时，应满足：

- 手柄 A/B 不再维护两份大状态机。
- 泵 A/B 只保留硬件通道和运行状态差异，不重复完整业务算法。
- 脚踏三种类型具有清楚的独立处理函数和共用门禁。
- `Pubinterface`不再同时拥有所有状态和所有业务动作。
- 外控收包、命令、状态上传和任务时序边界清楚。
- 公共状态的写入者显著减少，并能说明每类字段由谁负责。
- 所有触碰函数具有直白中文注释。
- 任务、协议、映射、安全门禁和实机行为与稳定基线一致。
