# FootControlTask 行为逻辑简化设计

## 1. 目标

本轮只重构 `User/Application/Beep/sscFOOT.c` 中的 `FootControlTask()` 行为逻辑，使单踏板、双段踏板和双踏板左右侧的调用关系更直白，减少大函数中的重复启动、停止和释放代码。

本轮属于行为等价重构，不增加新功能，不修正尚未单独复现的历史分支差异。

## 2. 明确不改的范围

- 不修改 `Foot_ParseDataS()`，UART4 收包、脚踏上线识别、定标值解析、按键解析和掉线计时保持原样。
- 不修改 UART4 协议、帧字段、定标值判断和串口发送命令。
- 不修改 `SscFootControlTask_Init()` 中的 10ms 解析周期和 25ms 行为周期。
- 不修改 `FootMsgQueue` 长度 5 和非阻塞收发方式。
- 不启用未接入启动链的 `PedalRecvTask_Init()`。
- 不修改独立线程栈、任务调度器、控制权编号、报警码、泵类型、A/B 硬件映射和屏幕地址。
- 不新增业务 `.c/.h` 文件，不调整 EIDE 或工程源文件清单。

## 3. 现有问题

当前 `FootControlTask()` 同时承担以下职责：

1. 处理其它控制源占用时的脚踏消息丢弃。
2. 处理脚踏上线、掉线和控制方式切换。
3. 处理单踏板的比例调速、启动和释放去抖。
4. 处理双段踏板的轻踩注水和深踩电机运行。
5. 处理双踏板左右侧的通道切换、切换去抖和松脚后再运行。
6. 处理公共接头、压力停机、外控、手柄连接和 owner 申请等安全门禁。
7. 处理电机停止、注水泵停止、报警清理和控制权释放。

这些逻辑集中在一个约 874 行的函数中。大量分支重复相同的门禁和状态写入，导致维护时难以确认某次修改影响单踏板、双段踏板还是双踏板左右侧。

## 4. 采用方案

采用“原文件内提取静态函数”的方式，不拆文件，不引入回调表或通用状态机。

`FootControlTask()` 重构后只保留以下顺序：

1. 检查是否被其它控制源占用；若占用，按原规则丢弃一个队列消息并返回。
2. 非阻塞读取一条脚踏消息。
3. 仅在收到新消息时处理上线或掉线边沿。
4. 若当前保存的脚踏状态为在线，按脚踏类型调用对应处理函数。
5. 本周期所有输出均停止时，调用原控制权释放接口。

计划在 `sscFOOT.c` 内增加以下静态函数：

- `Foot_HandleConnectionUpdate()`：只处理收到新队列消息时的上线、掉线、控制方式和显示刷新。
- `Foot_ProcessSinglePedal()`：只处理单踏板低点到高点的比例运行和释放去抖。
- `Foot_ProcessTwoStagePedal()`：只处理双段踏板的轻踩注水、深踩电机和完全释放。
- `Foot_ProcessDoublePedal()`：按原顺序先处理左踏板，再处理右踏板。
- `Foot_ProcessDoublePedalLeft()`：保留左踏板使用 `switchhandle_counts`、切换 A 通道和左侧释放规则。
- `Foot_ProcessDoublePedalRight()`：保留右踏板使用 `switchhandle_countss`、切换 B 通道和右侧释放规则。

已有的速度换算、安全锁存、报警处理、注水泵启停函数继续使用，不再为一次性调用增加新的包装层。

## 5. 必须保持的执行顺序

以下顺序属于产品行为，提取函数时不得调整：

- 其它 owner 占用时先丢弃队列消息，再立即返回。
- 脚踏掉线时先清脚踏运行来源和电机运行，再清控制方式锁存并刷新显示。
- 单踏板先通过控制方式、外控、公共接头和 owner 门禁，再写实际速度和运行标志，最后启动联动注水泵。
- 双段踏板和双踏板允许轻踩阶段先启动注水泵；进入电机段失败时必须使用现有撤销入口停泵并清运行请求。
- 压力停机和公共接头缺刀具锁存期间，保持踩下不能自动重新启动，必须等真实松脚。
- 双踏板左侧和右侧继续使用各自独立的切换计数，不合并为一个共享计数。
- 跨通道切换成功后仍需等待对应踏板释放，再允许新通道运行。
- 双踏板周期内保持先处理左侧、再处理右侧的顺序。
- 周期末继续调用 `ControlArbitration_ExitLocalControlIfIdle(CONTROL_OWNER_FOOT)`。

## 6. 保留的历史差异

以下差异没有独立缺陷复现，本轮原样保留：

- JTB 轻踩时，A 注水泵使用当前通道默认注水流量，B 注水泵继续使用现有 `pumpMessageB.speed_work`。
- JTD 左右踏板分别使用自己的 AD、低中高定标值、控制标志和切换计数。
- 双踏板部分释放分支对另一侧控制标志或释放状态的检查保持当前代码含义。
- 单踏板专用的 3 个周期释放去抖不扩展到其它踏板类型。
- 双踏板切换使用 10 个周期确认，计数阈值和蜂鸣时机不变。

若后续确认这些差异属于产品缺陷，应另开独立修复阶段，不与本轮结构重构混合。

## 7. 注释要求

- 每个新增静态函数前写明“函数功能、输入参数、返回参数”。
- 关键状态写入必须说明影响电机、泵、报警、通道切换或控制权中的哪一项。
- 注释使用现场可理解的直白中文，不复述代码表面动作。
- 不批量改写 `Foot_ParseDataS()` 和其它未触碰函数的旧注释。

## 8. 验证方案

### 8.1 修改前行为锁定

创建一次性静态校验脚本并先运行失败，校验目标包括：

- 新的分类型处理函数在修改前不存在。
- UART4 解析函数和任务初始化函数的文本哈希被记录。
- 队列长度、10ms/25ms 周期、踏板类型编号、释放去抖和切换去抖常量被记录。
- 关键安全门禁、A/B 切换字段和泵联动调用仍可检索。

### 8.2 修改后静态校验

- `FootControlTask()` 只负责调度，不再直接包含三类踏板的大段业务分支。
- 三类踏板及双踏板左右侧各有明确静态函数。
- `Foot_ParseDataS()` 和 `SscFootControlTask_Init()` 与修改前文本一致。
- UART4 协议、队列、周期、阈值、报警码和控制权接口均未变化。
- 临时校验脚本执行后立即删除。

### 8.3 构建和 map

- 使用 EIDE/AC5 全量构建，要求 0 error，不增加当前 20 个 warning。
- 对比 map 中 `FootControlTask()`、`Foot_ParseDataS()` 和新增静态函数符号。
- `FootControlTask()` 本体应显著缩短；ROM 如有增加，必须定位到函数调用和栈帧，不以资源下降代替行为验证。
- 不打开 Keil。

### 8.4 实机回归

- 单踏板：踩下比例调速、瞬时低值去抖、松脚停止、压力停机后保持踩下不重启。
- 双段踏板：轻踩只启动注水泵、深踩启动电机、回到轻踩区停止电机、完全释放停止泵。
- 双踏板：左右分别控制当前通道、跨 A/B 通道切换、切换蜂鸣、切换后必须松脚再运行。
- 安全门禁：手柄未连接、公共接头缺刀具、外控占用、压力停机、其它 owner 占用。
- 状态恢复：脚踏上线、掉线、重新插入、报警清理和屏幕控制方式高亮。

实机确认前不提交脚踏生产代码；出现任何行为差异时只回退本轮脚踏重构。
